# 真机连接与 WSL2 NAT 限制

本文说明：为什么当前环境（WSL2 里的 Ubuntu 22.04）**连不上真机**，以及有哪几条可行的对策。
纯仿真不受这些限制影响。

## 1. 真机的网络拓扑

| 角色 | 地址 | 说明 |
| --- | --- | --- |
| 开发 PC（官方要求） | `10.1.1.99`（静态 IP） | 与机器人同网段 |
| 运控板 | `10.1.1.100` | HAL / MC / 交互服务都在这里 |
| 大脑板 | `10.1.1.101` | AI 与感知 |
| 无线 AP | SSID `Q1-<sn后10位>` | 机器人自带热点 |

开发 PC 与两块板子之间走 **LAN + FastDDS（RTPS over UDP）**，服务与话题都是 DDS 发现出来的。

## 2. 当前环境为什么连不上

本机是 **Windows 10 build 19045**，WSL2 只能工作在 **NAT 模式**：

```
WSL2 内的地址：  172.21.204.166/20   （WSL 自己的虚拟网段）
默认网关：       172.21.192.1        （Windows 主机侧虚拟网卡）
Windows 主机：   10.1.1.x            （真正加入机器人网段的只有它）
```

由此产生三个硬问题：

1. **WSL2 不在 `10.1.1.0/24` 网段里**，二层广播到不了机器人，DDS 的多播发现（239.255.0.1）出不去。
2. **DDS 会把自己的 locator 通告成 `172.21.x.x`**。即使单播能通，机器人按这个地址回连也必然失败
   —— 那是 WSL 的虚拟地址，只在 Windows 主机内部有意义。
3. **`networkingMode=mirrored`（让 WSL 共享主机网络栈）需要 Windows 11 22H2+**，
   Windows 10 不支持，所以"最省事的那个开关"在本机不存在。

因此：**"在 WSL 里直接 `ros2 topic list` 看真机"这条路，在本机是走不通的**，
不是配置没调对，而是网络模型决定的。

## 3. 对策（按推荐程度排序）

### 对策 1：把代码部署到机器人板子上运行 ★最推荐

不跨 NAT、不需要任何中继，和厂商示例的预期用法一致：

```bash
# 先让 Windows 主机连上机器人的 AP / 同网段，从 Windows 侧操作
scp -r aimdk_sdk/ user@10.1.1.100:~/          # 板子上的账号见厂商文档
ssh user@10.1.1.100
# 在板子上直接跑 SDK 示例
python3 examples/hal/joint_control.py
```

优点：零网络改造、延迟最低、也最接近实际部署形态。
代价：开发调试要 ssh，不能用本机 RViz2 直接看真机 TF。

### 对策 2：在 Windows 上做 UDP 中继 + FastDDS locator 覆盖

原理：Windows 主机同时连 着 `10.1.1.x`（机器人网段）和 WSL 虚拟网段（`172.21.x`），
所以它可以当转发点。但**必须同时**做两件事：

1. Windows 上写一个 UDP 中继：把 WSL 发出的包源地址改写成 `10.1.1.99` 发往机器人，
   并把机器人的回包转回 WSL。**只用 `netsh interface portproxy` 不够**，
   因为它只支持 TCP，而 DDS 主要走 UDP。
2. WSL 侧用 FastDDS 的 XML 配置**覆盖本机通告的 locator**（把 `172.21.x.x` 换成 `10.1.1.99`），
   否则机器人仍然会往一个不可达地址回包。
   同时要**关掉多播发现、改成 initial peers 单播**。

配置文件骨架见 `ros2/fastdds_unicast.xml`（**未在真机上验证过**，因为它需要真实机器人才能验证；
这里只提供起点和调参位置）。

### 对策 3：换 WSL 网络模式

在 `C:\Users\<你>\.wslconfig` 里：

```ini
[wsl2]
networkingMode=mirrored
```

**本机不适用**：需要 Windows 11 22H2 及以上。若将来升级到 Win11，这一步是最省事的做法
（mirrored 模式下 WSL 直接用主机网卡，能正常收发多播）。

### 对策 4：在 Windows 原生环境跑 ROS2

官方只提供 Ubuntu 的二进制包，Windows 原生安装并不被支持。
如果非要走这条路，可行的是**另找一台 Ubuntu 机器**接在机器人网段上，
把它当作开发机 —— 这比在 Windows 上折腾更可靠。

## 4. 结论

| 需求 | 本机能否满足 | 建议做法 |
| --- | --- | --- |
| 纯仿真（MuJoCo / RViz2 看模型） | ✅ 完全可以 | 就用现在这套环境，不受 NAT 影响 |
| 用 SDK 编译、读代码、改代码 | ✅ 可以 | 编译在这边做，只把可执行文件/脚本拷到板子 |
| 让 WSL2 直接发现真机的 DDS 服务 | ❌ 不行 | 用对策 1（部署到板子），或对策 2（中继+locator 覆盖） |
| 在本机 RViz2 看真机实时 TF | ❌ 不行 | 同上；真机数据可让板子转发成 ROS2 话题再由主机订阅 |

## 5. 安全提醒

厂商文档明确警告：**低层关节伺服接口有物理风险**。
本环境只驱动仿真，从未、也不应该直接向真机下发低层关节指令。
在做任何真机低层运动开发之前，必须先读 `友好用户使用声明.md`（在 SDK 压缩包内）。
